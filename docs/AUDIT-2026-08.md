## Unbounded scrollback — DONE as far as "possible" (2026-08-04)

**`max_output_lines = 0` now means unlimited, and it works.** Steps 5–8 of the
plan below have landed:

| Step | Commit | What |
|---|---|---|
| 5 | `81fa698` | Idle worlds stop repainting (the 10 Hz timer only drains when there is something to flush), and a packet costs one invalidation instead of three |
| 6 | `e51fbfb` | The jump index is a deque sized from the content, not a fixed array sized from the cap — removes the latent heap overrun AND the O(cap/100) shuffle per eviction |
| 7 | `6dcaf85` | `OPT_ZERO_UNLIMITED`: 0 is legal below the 200 floor, ceiling raised to 100,000,000, round-trips through the world file |
| 8 | `5fa24cf` | Scroll geometry is 64-bit; the products saturate instead of wrapping negative past ~143M visual rows |

Two things worth carrying forward:

- **Step 7's real difficulty was not the option table.** `Save_XML_number` omits
  zeros ("default of zero does not need to be written") and the loader keeps the
  member's current value for an absent attribute — so "absent" means *keep the
  default*, not *zero*, and unlimited silently came back as 5,000 on the next
  load. The fix is a `bWriteZero` opt-in, defaulted false. Any future option
  where 0 is a real setting rather than "unset" has the same trap.

  **Correction, 2026-08-22: not just future ones.** Four rows already had it —
  `pixel_offset` (default 1), `fade_output_opacity_percent` (20),
  `tool_tip_visible_time` (5000) and `tool_tip_start_time` (400) — each of which
  accepts a meaningful 0 and each of which silently reverted to its default on
  the next save. Measured, not inferred: none of the four attributes reached the
  file. `docs/UPSTREAM-BUGS.md` 101. The opt-in is now derived rather than
  declared (write the zero whenever the option's *default* is non-zero), because
  a per-row flag only ever protects the rows somebody thought about — which is
  what this bullet's own last sentence assumed would be enough.
- **`RemoveChunk` walked `JUMP_SIZE` head nodes unconditionally.** Safe for every
  legal cap (floor 200, JUMP_SIZE 100), but it aborts on an out-of-range cap
  written straight into `m_maxlines` — which the world loader and the tests can
  both do. Now stops at an empty list.

**What is still true at scale**, i.e. steps 9–12 remain open and unlimited is
"possible, not yet pleasant": copy still round-trips through UTF-32. The hard
ceiling is wx's int virtual size, ~143M visual rows; lifting that means
scrolling by row rather than by pixel.

**The second copy of the scrollback is gone** (2026-08-05, the pull model
merged) — 548 → ~340 bytes/line, a 38% cut. See below.

**Two claims in this paragraph went stale and were corrected on 2026-08-04** —
the standing warning about these files, applied to this file:

- *"a palette change is still O(buffer) (`RebuildOutputView`)"* — no longer
  true. `CWorldChildFrame` recolours **in place** through
  `COutputPane::RecolourFromPalette` (`wx_world_child.cpp:4263`): runs carry
  the style inputs their colours were resolved from, so the pane re-runs the
  same `pal::resolveStyleColours` the document does. Colours cannot change
  metrics, so the wrap cache, scroll position and selection all stay valid.
- *"Find still scans twice per keypress"* — no longer true.
  `COutputPane::RebuildFindCache` caches the matching line indices and is
  guarded by `m_bufferGen`, which every buffer mutation bumps (append, trim,
  head/tail delete, clear), so a repeat search with an unchanged buffer costs
  nothing.

Neither had a plan step of its own; both fell out of other work, which is
exactly how a per-item backlog goes stale.

### The pull model: measured, finished, merged (2026-08-05)

The pane keeps no line content of its own; it fetches each line from the engine
as it paints, so the second copy of the scrollback is gone. **340 bytes/line
against 548**, measured on 200,000 unlimited lines — a 38% cut, ~42 MB at 200k.
Both figures are with the 64-byte `SOutputRun` already in place, so this is on
top of that. Branch `pull-model-worldview` keeps the blow-by-blow; main has it
as one commit.

**What the spike had left undone**, and what the completion is really about:

It introduced `LineCountI()` — "how many lines does the pane know about", the
engine's count when the pull seam is wired — and converted the READERS to it.
It did not convert the **mutators**, which still guarded with a count and then
operated on `m_lines`, empty under the pull model. All three popped an empty
deque; `DeleteTailLines` is `world.DeleteLines(n)` and predates the clear
commands entirely, so the crash was reachable on the spike's own terms.

The invariant that resolves it, now stated once in `DerivedTargetLength()`:
**the engine owns the line set, the pane owns only what it derives from it**,
so a pane-side trim targets the length of that derived data. Trimming to
`m_maxLines` could not even terminate — popping the pane's wrap cache does not
change what `LineCountI()` reports.

**And one bug that came from main.** `CMUSHclientDoc::DeleteHeadLines` notified
the view *before* rebuilding the jump index, leaving every entry pointing at a
freed node while the view was being told — and that notification is not
passive, since `UpdateScrollbars` can force a synchronous repaint and a repaint
resolves line indices through `GetLinePosition`. A use-after-free that only
fires when a paint lands in the window: 3-to-5 runs in 10. Latent in the push
model, where the pane never reads back through the engine.

**Two mutations survived at first, and the FIXTURE was wrong both times**, not
the assertions — worth remembering, because both look like strong tests:

- `LineCount()` reports the *engine's* number under the pull seam, so it agrees
  by construction no matter what the pane did. Only the derived length can show
  drift, which is why `DerivedLength()` exists.
- Draining once at the end let the engine finish evicting before the pane saw
  anything, so the pane could never be holding more lines than the engine —
  the one state the capacity trim exists to resolve. The drain is interleaved
  now, as a connected world's is.

## Decisions needed

These are the items where the right answer is a judgement call, not a fix.

### 1. `App.m_strWorldList` — RESOLVED 2026-08-02

Wade chose Windows semantics; implemented in `7a37b42`. The port no longer writes
the list at all. Kept below for the reasoning.

#### Original write-up

`platform/wx_mfc_impl.cpp` adds every world to `App.m_strWorldList` when it is
opened (`:1969`) or saved (`:2074`, `:2366`), and removes it when it is closed.
On Windows that list has exactly one writer — the Global Preferences page
(`dialogs/global_prefs/GlobalPrefs.cpp:1441`) — and it means "open these at
startup", curated by the user.

So the port has quietly repurposed a user setting as session state. The effect
is nice (your worlds come back) but it destroys the curated list, and it is
undocumented in `docs/UPSTREAM-DIVERGENCES.md`. Same shape as the `wrap_column`
bug fixed in `bec3611`: the port writing over something the user owns.

Options: keep it and record it as a divergence; keep the behaviour but move it
to a separate port-only key so the Windows setting is left alone; or drop it and
restore Windows semantics.

### 2. Default custom-colour palette on world open — RESOLVED 2026-08-04

It needed no decision in the end: the suspicion was right and there was no
trade-off to weigh. The document constructor already installs Gammon's palette
(`SetDefaultAnsiColours` + `SetDefaultCustomColours`, `doc_construct.cpp:316-319`)
and neither `OnNewDocument` nor `OnOpenDocument` resets it — `SetDefaults(false)`
walks `OptionsTable` only, and the colour arrays are not option-table items. So
both hooks were destroying correct values.

Worse than cosmetic: the world-file loader keeps the current member value when an
attribute is absent, so a world file with no `<custom>` section got the hook's
re-seed of `m_customtext[i] = m_normalcolour[i % 8]` on a black background —
which made **custom colour 1 black-on-black**, and notes (`m_iNoteTextColour = 4`)
lost the readable blue the constructor gives them.

Both hooks now call `wx_seed_new_world_defaults` (`wx_mfc_impl.cpp:1960`), which
deliberately touches no colours at all; the ANSI tables they also wrote by hand
turned out to be byte-for-byte what `SetDefaultAnsiColours` had already written,
so those are simply gone. Pinned by `--gui-bridge-selftest` §3.

### 3. Re-wrap on resize — RESOLVED 2026-08-04: leave as-is

Wade's call: MUSHclient hard-wraps into the line list on both platforms and
history has never reflowed. Keep it that way. Soft-wrap is separately pinned
(the engine change is small, but `CMUSHView` has no wrapping renderer at all —
every draw, hit-test, selection and scroll path is `line * m_FontHeight` — and
the public API is denominated in wrapped lines, `GetLineInfo(n, 3)` literally
exposing `hard_return`).

### 4. How far to take the unbounded-scrollback work — RESOLVED 2026-08-04: all the way

Wade wants infinite scrollback, not merely reachable scrollback. Steps 5-8 are
done and `max_output_lines = 0` works; steps 9-12 are what make a million-line
buffer pleasant rather than merely possible, and are now in scope.

## printf format attributes — the remaining 65 warnings

`MC_PRINTF_FORMAT` (guarded: real on GCC/clang, nothing on MSVC) is now on
TFormat, CFormat, CString::Format, CMUSHclientDoc::Trace, ThrowErrorException and
CErrorException.  It found seven real bugs, fixed in `73f30e7`.

65 width-mismatch warnings remain.  **They are deliberately not "fixed" yet**,
because the obvious fix is wrong:

    strMsg.Format ("%ld lines", someInt);     // warns on macOS

On macOS `long` is 64-bit, so `%ld` against an `int` is a mismatch.  On the
32-bit Windows build this project also targets, `long` and `int` are BOTH 32-bit
and the existing specifier is correct.  Changing `%ld` to `%d` would silence
macOS and introduce the mismatch on Windows.

The correct shape is to cast the ARGUMENT and leave the specifier alone:

    strMsg.Format ("%ld lines", (long) someInt);

which is right on both.  That makes it a mechanical sweep of 65 sites in
Windows-shared code — worth doing deliberately, in its own commit, not folded
into a bug fix.

Severity: low.  On AArch64 and x86-64 every integral vararg occupies an 8-byte
slot with the value extended, so `%ld` against an `int` reads the right value.
The one direction that can actually be wrong is `%d` against a `long` (24 of the
65), which truncates above 2^31 — reachable only by a line or byte count past two
billion, which is exactly the territory the unbounded-scrollback work opens up.

**Recorded as language divergences, not bugs** — the suite prints why it is
skipping rather than quietly not testing:

- an explicit `nil`/`None`/`undef` return stops in Lua but keeps going in the
  other five: those languages return it from a function that falls off the end,
  so the engine cannot tell the two apart and "keep going" is the safe reading;
- returning a structure cannot be told from returning a string in Tcl, where
  every value IS its string representation;
- Lua and JavaScript cannot separate "the script defined this name" from "the
  language did" (Lua resolves through `_G`'s metatable into the world library;
  JavaScriptCore's built-ins are own properties of the global object) without
  changing resolution semantics plugins rely on;
- Python and Ruby model a numeric parameter as a float and say so.

**Still open**, in descending value — none verified beyond the reading agent:

1. ~~**Named regexp wildcards are never marshalled**~~ — **NOT a bug; the entry
   was wrong.**  Checked against the Windows call site (`doc_shared.cpp`): the
   COM arm builds a 1-relative SAFEARRAY of `MAX_WILDCARDS` POSITIONAL wildcards
   and no named captures, so VBScript / JScript / PerlScript on Windows do not
   get them either.  Only Lua does, on both platforms, because `lua_scripting.cpp`
   walks `PCRE_INFO_NAMETABLE` itself.  The five embedded engines are faithful.

   Three genuine differences sit here.  The **content** one is now fixed; the two
   **shape** ones remain open questions for Wade, because either answer breaks
   someone.

   - **Content — FIXED 2026-08-03.**  The COM arm passes
     `trigger_item->wildcards[]`, which `evaluate.cpp` filled through
     `FixWildcard`; the engines built their own list from the regexp, raw.  So
     the per-trigger option **"convert wildcards to lower case"**
     (`CTrigger::bLowercaseWildcard`) worked on Windows and did nothing in five
     of the port's six languages.  The five now fold, via the new
     `t_regexp::GetCallbackWildcards`; **Lua still does not**, because Lua reads
     the regexp raw on Windows too.  That asymmetry is upstream's, and is pinned
     from both sides now — `tests/test_triggers.cpp` headless, and
     `battery_wildcards` + `battery_trigger_callsite` in
     `platform/engines_selftest.cpp` for all six languages.  Both mutation-checked
     (removing the fold fails 10 engine assertions and one unit test; dropping
     only the call-site argument fails exactly the 5 trigger-call-site ones).

     **DECIDED 2026-08-03 (Wade): not replicated.**  `FixWildcard`'s *other*
     half escapes `\`, `"` and (for `perlscript`) `$` when the trigger's
     send-to is **Script**.  The evidence that it is an upstream accident rather
     than a policy, in rising order of weight:

     1. it branches on COM *language names* (`"vbscript"`, `"perlscript"`),
        i.e. rules for generating a string literal in that language's SOURCE —
        irrelevant to a value crossing as a VARIANT;
     2. it is gated on `iSendTo`, which describes the trigger's **send text**,
        while the callback fires with no reference to `iSendTo` at all
        (`ProcessPreviousLine.cpp:914`);
     3. the escaped array also feeds the **clipboard**
        (`ProcessPreviousLine.cpp:1108`), so a send-to-Script trigger put
        `C:\\path` on the user's clipboard;
     4. decisively — the `%1` substitution path does NOT read the stored array.
        It re-derives from the regexp and calls `FixWildcard` itself
        (`evaluate.cpp:1343`, `:1388`).  So the escaping at the array-fill site
        (`:489`) reaches only consumers that treat the string as DATA (the COM
        SAFEARRAY, `GetTriggerInfo`/`GetAliasInfo` 101-110, the clipboard) and
        is not what makes `%1` safe for the one path that splices into source.

     Corroboration inside Lua: a Lua world's `%1` substitution IS escaped
     (`"lua"` takes the non-VBScript branch) while its callback is not — so even
     upstream, escaping tracks *substitution*, not *wildcards*.

     Replicating it would also need a port-language → COM-language name map
     (`"perl"` vs `"perlscript"`) to get the `$` rule right.  This is a
     macOS-vs-Windows difference, so it lives as a port comment (`regexp.h`,
     `GetCallbackWildcards`) rather than in `docs/UPSTREAM-DIVERGENCES.md`,
     which is for divergences applied to BOTH builds.
   - **Index base.**  Windows' COM array is 1-relative with no `[0]`; the port's
     engines followed Lua and put the WHOLE MATCH at `[0]`.  First capture is at
     `[1]` either way.  Note the COM array puts the whole matching line **last**,
     at index 10 — the same convention as `GetTriggerInfo(110)`.
   - **Length.**  Windows always hands over `MAX_WILDCARDS` (10) slots, so
     `wildcards(7)` on a two-group pattern is `""`; the port sizes the array to
     `ncapt + 1`, so the same read is an IndexError / `undefined`.

   **Both shape items are punted to the Windows run** (2026-08-03, Wade) — the
   question is on the checklist as `docs/WINDOWS-VALIDATION.md` § 4c-octies-bis,
   which asks for the observed index base, length and whole-match position from
   a real ActiveScript engine.  Nothing changes in the port until that comes
   back.

   The reason it has to be measured rather than read: what a
   Windows script actually *indexes* depends on its COM bridge.  pywin32
   marshals a SAFEARRAY to a plain tuple and drops the lower bound — if so,
   Windows-with-ActivePython sees `%1` at index 0 and the whole line at index 9,
   a third shape agreeing with neither.  Unverifiable without a Windows box.

3. ~~**World proxies hold a raw, unowned `CMUSHclientDoc*`**~~ **Done**: there is

## Steps 11(b) and 11(d): blocked on verification, not on effort (2026-08-04)

Both are real wins and both are **deliberately not attempted**, because each
fails SILENTLY and neither can be verified on this machine.

**11(b) — intersect OnPaint's row range with the update region.** The row loop
is already bounded to the visible viewport, so the remaining win needs the
matching half: callers using `RefreshRect` for localised changes (the pending
prompt row, selection-drag deltas) instead of a whole-pane `Refresh`. The two
must land together or nothing gets faster.

The blocker is `dc.Clear()`. If `wxAutoBufferedPaintDC::Clear` clears only the
update region, narrowing the row loop is correct. If it clears the whole
buffer, rows outside the update region are erased and never redrawn — visual
corruption, on a scrolling MUD, that no assertion in the suite would notice. The
answer is platform- and wx-version-specific and has to be established
empirically before the change is safe.

## Step 11(b) is REFUTED by measurement too — do not implement it (2026-08-05)

The correctness blocker is gone (below), and then the same question that killed
11(a) was asked of it: **how much is there to win?**
`--extended-selftest=paint-cost` times real repaints of a 960x640 pane holding
3,000 lines of three-run styled text:

```
full-viewport repaint: 0.333 ms      (~40 rows on screen, ~0.008 ms per row)
```

So narrowing the row loop to a single row could save **at most 0.33 ms per
paint**, and only when the update region really is one row. The display drain
runs at 10 Hz, so the ceiling is about 3 ms per second — a third of one percent
of one core — and that is the ceiling, not the expectation.

Against that: the change needs the row range intersected with the update region
in a coordinate space that is already shifted twice (the text rectangle origin
and `m_pixelOffset`), plus converting the pane's **30** `Refresh()` calls to
`RefreshRect` — there are currently **zero**. Its failure mode is rows that are
silently never redrawn, i.e. scrolling corruption, which no assertion in the
suite would catch and which cannot be checked here without a person watching
the screen.

**Not worth it.** A third of a millisecond does not buy intricate arithmetic in
the paint path with a silent-corruption failure mode. Recorded with the number
so it is not re-proposed; the harness stays registered as
`extended_paint_cost`, so anyone revisiting can re-measure in one command
rather than re-deriving.

The correctness finding stands on its own and is worth keeping:

**Clear() ANSWERED 2026-08-05, once the loop-running selftest mode existed.**
`--extended-selftest=clear-semantics` invalidates a 20x20 rect on a real shown
window and reads what the second paint is handed:

```
invalidated 0,0 20x20; update region 0,0 20x20; paint DC clip 0,0 20x20
```

**wx hands the paint DC a clipping box exactly equal to the update region**, so
`Clear()` physically cannot write outside it whatever it intends, and narrowing
`OnPaint`'s row loop to that region is safe **by construction** rather than by
argument. The obvious test — read a pixel back and see what colour it is — was
tried first and is NOT trustworthy here: wxOSX cannot reliably blit out of a
`wxClientDC` (`platform/wx_composite_selftest.cpp` documents the same thing and
works around it), and the probe duly read the default window grey rather than
either colour. The clipping box needs no read-back and is exact.

**What this does and does not unlock.** The correctness blocker is gone. The
PAYOFF still needs the other half the original analysis named: callers must
invalidate narrowly (`RefreshRect`) instead of whole-window `Refresh()`.
Because the DC is already clipped, everything drawn outside the update region
is *already* being discarded by the graphics layer — so narrowing the loop
saves the CPU of building and issuing draw calls that get thrown away, and that
saving is proportional to how small the update region is. With every caller
still invalidating the whole window, narrowing the loop alone buys nothing.
Do the two together or not at all.

**The original analysis, kept because it is why this took a mode to answer:**
`COutputPane::OnPaint` **never runs inside an in-app selftest.** Instrumented
with a counter and driven three ways, on both harnesses:

| harness | window | 200 × `Refresh` + … | `OnPaint` calls |
|---|---|---|---|
| `--outputpane-selftest` | offscreen (-4000,-4000) | `Update()` | 2 |
| `--world-frame-selftest` | onscreen (50,50), shown | `Update()` | 0 |
| `--world-frame-selftest` | onscreen (50,50), shown | `wxYield()` | 0 |

The cause is structural, not a harness detail: every selftest runs inside
`wxApp::OnInit` and `std::exit`s before `OnRun()`, so the event loop AppKit
issues `drawRect:` from has never started. Neither `Update()` nor `wxYield()`
substitutes for it. (The "0.005 ms per repaint" the first row appears to report
is not a fast paint — it is the absence of one.)

So neither half of 11(b) is answerable here. The `Clear()` semantics need a
real paint into a real backing store, and the row loop cannot be timed without
one. **This is now a measurement rather than a judgement.**

### What else the unreachable paint path means

Worth stating separately, because it is a coverage boundary for the whole
selftest mechanism rather than a fact about 11(b). Anything reachable ONLY from
`OnPaint` has no in-app coverage:

- **`ON_PLUGIN_DRAW_OUTPUT_WINDOW`** (`m_fn_draw_output_window`) fires from the
  paint handler and nowhere else.
- **The background image** (`m_fn_draw_background_image`, world
  `SetBackgroundImage`), likewise.
- **The char-metric re-measure** at the top of `OnPaint` — the arm that
  notices the paint DC disagrees with `m_charW`/`m_lineH` and `CallAfter`s a
  wrap-cache rebuild. This is the HiDPI correction; it has never executed under
  test.

The miniwindow compositor is *not* in this list: the composite selftest calls
`wx_composite_miniwindows` directly rather than through a paint, which is
exactly why it has real coverage. That is the pattern to copy — where a
paint-only path has engine-shaped logic, give it an entry point the test can
call, rather than trying to provoke a paint.

**11(d) — cache the transparent miniwindow's masked bitmap. DONE 2026-08-05.**

The blocker was recorded as "there is no choke point: the ~49 `Window*` draw
ops each call `srf->…(m_surfaceId, …)` directly, so a change counter means
editing every one of them in Windows-shared code". That was looking one layer
too high. Every one of those calls lands in **`pal::WxSurface`**, whose ops all
begin `Surf* s = surf(id)` — 21 sites, one port-only file. The counter lives
there, bumped by a `mutate(id)` helper that the 16 mutating ops call instead of
`surf(id)`; the 5 readers keep `surf(id)`.

Two details that make it safe rather than merely plausible:

- The counter is **adapter-wide, not per-surface**, so a generation identifies
  a content-state globally. Per-surface counters would both start at 1 and
  `SurfaceId`s are recycled, so a cache keyed by (surface, generation) could be
  handed an entry belonging to a destroyed surface mutated the same number of
  times. `0` is reserved to mean "this adapter does not track it", which makes
  an adapter without support slow rather than stale.
- The "single missed site" failure is now **mechanically caught**: the surface
  selftest exercises every mutating op and asserts the generation moved, and
  every reader and asserts it did not. Reverting one `mutate` to `surf` fails
  that op's check AND the end-to-end pixel check in the composite selftest.

The cache itself is keyed on the generation plus the geometry the mask depends
on, with a sweep for windows the document no longer has. That sweep has to sit
ABOVE the compositor's empty-order early-out — deleting the LAST miniwindow is
precisely the case where nothing is composited afterwards, so a sweep below it
would hold that window's bitmap forever. The test caught that.

**Neither scales with the scrollback**, which is what the unbounded-buffer work
is actually for: 11(b) is per-paint, 11(d) was per-miniwindow-per-paint. 11(b)
still wants someone watching the screen; 11(d) turned out not to, once the
choke point was found one layer down.

## Step 11(a) is REFUTED by measurement — do not re-attempt (2026-08-04)

The plan's first paint-throughput item was: *"DrawRunChunk — measure the font's
natural advance once; when it matches m_charW draw whole chunks with one
DrawText, keeping the per-glyph path only when drift is detected."*

Implemented, measured, and **reverted**. The premise is false on macOS.

`GetPartialTextExtents` over printable ASCII in the default output font reports
cumulative widths of **7, 14, 22, 29 …** — an advance of about **7.25 px** —
against an `m_charW` of **8**. The two never coincide, so the "matches" branch
never runs. A rendered A/B of the same string, per-glyph versus one `DrawText`,
confirms it: the bitmaps differ.

So the per-glyph loop is not a missed optimisation. It is **forced**: Core Text
advances are fractional, the column arithmetic (selection rectangles, click
hit-testing, wrap columns) is an integer grid, and one `DrawText` would place
glyphs where the grid says they are not. That is the bug that was already fixed
once.

Shipping the probe anyway would have added eight cache slots, a per-chunk ASCII
scan and two test hooks to enable a path that never executes — a net cost.

**The only real fix is bigger than this step:** make the grid match the font,
i.e. carry the fractional advance through the column arithmetic as well as the
drawing. That changes selection semantics and touches every consumer of
`m_charW`, and it is not what step 11 was scoped as. Left alone deliberately.

The remaining 11(b)-(e) items (update-region intersection, cached search-hit
ranges, the masked-bitmap cache, one hotspot hit-test per motion) are
independent of this and stand.

## Addendum (2026-08-24 bug hunt): miniwindow pixel writes convert the whole canvas, twice

Verified, not fixed. `platform/wx_gdi_compat.cpp`'s `wxgdi_write_bgra` has a
DIBSection fast path (`GetDIBForHDC`, a pointer add) and a fallback that runs
`bmp.ConvertToImage()` over the ENTIRE canvas, writes the requested region, then
rebuilds the entire canvas with `wxBitmap updated(img, 32)`. Every miniwindow
canvas takes the fallback: `CBitmap::CreateCanvasBitmap` builds a plain
`wxBitmap` via `CreateWithDIPSize` (never a DIBSection), so `GetDIBForHDC`
always misses. The read-side twin `wxgdi_read_bgra` was already fixed to convert
only the requested sub-region; the write side was not.

`WxSurface::writePixels` — the function that reaches `wxgdi_write_bgra` — is
called by `setPixel`, `fillRect`, `invertRect`, `floodFill`, `gradient` and
`blit`. So it is **not** only the per-pixel path: every `world.WindowRectOp`
fill, `world.WindowGradient` and `world.WindowDrawImage`/`BlendImage` on a
miniwindow converts the whole backing bitmap out and back. On a Retina panel a
500×400 miniwindow is 1000×800 = 800 000 physical pixels, so a single 1-pixel
`WindowSetPixel` moves ~2.4 MB out + ~3.2 MB back — an 800 000:1 amplification —
and a normal redraw of a map/status window that does a dozen rect/image ops pays
that a dozen times per frame.

**Fix direction, with its traps.** Mirror the read-side fix: touch only the
`w·scale × h·scale` pixels of the write region instead of the whole canvas.
`DrawBitmap` of a sub-image is O(region) but is WRONG — it composites (source-
over) rather than replaces, so a semi-transparent pixel written back after a
`readPixels` read-modify-write would blend with itself. The correct tool is
`wxAlphaPixelData` (raw in-place pixel access to the selected bitmap), which
needs (a) the same `SelectObject(wxNullBitmap)` / re-select dance the current
code already does, and (b) care with wxOSX's **premultiplied** alpha — the
existing `wxImage` path is non-premultiplied, so a naive `wxAlphaPixelData`
rewrite would corrupt colours unless it premultiplies on write and un-
premultiplies on the read side to match. Untestable in the headless harness
(WxSurface is GUI-only; the composite selftest checks correctness, not cost), so
this wants a Retina-display eyeball on real plugin output as part of the change.
