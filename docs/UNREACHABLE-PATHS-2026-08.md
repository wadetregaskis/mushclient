### What the cluster pass actually found

Three defects the extractions turned up, none of them the finding they were
aimed at:

* **The `DefaultWorldFileName` hoist was not behaviour-identical.** The old code
  converted the world name from UTF-8 *first*, so an invalid name became an
  empty `wxString` and fell into the `world.mcl` fallback. Converting last let
  the invalid name survive the scrub and die in `FromUTF8` — an **empty
  filename in the Save-As dialog**. Caught by the adversarial reviewer with a
  compiled probe, fixed before merge.
* **`UMessageBox`'s headless fallback answered the wrong button.** Both copies
  said `(nType & MB_YESNO) ? IDNO : IDOK`; `MB_YESNOCANCEL` is 3 and `MB_YESNO`
  is 4, so `3 & 4 == 0` answered a three-way *save your changes?* prompt with
  `IDOK` — which the caller falls straight through, closing the world and
  discarding the work. Same mis-reading `hook_message_box`'s own comment
  records being fixed there. Now one shared decision, `static_assert`ed.
* **The Activity window rebuilt its whole list four times a second, for ever,**
  on a non-positive refresh interval. The member is unsigned, so a stored −5
  read back as 4294967291 and passed the old `> 0` guard, which then cast it
  back to −5 *inside* the guard — and `elapsed >= -5000` is true on every tick.
  The comment written beside the fix stated the bug backwards ("never refresh")
  until a reviewer compiled the old expression; corrected before merge.

And one **coverage hole the work itself left**: the no-echo extraction was
tested while its *wiring* was not — deleting the `PollNoEcho()` call from the
world timer left the entire suite green, with a real MUD password prompt going
to a visible, echoing control. Found by a reviewer's mutation, closed with an
arm that touches only `m_bNoEcho` and lets the timer find it.

### Output pane render path — COutputPane::OnPaint and its paint-only callees (platform/wx_outputpane.cpp)

**1. Wrapped-line selection geometry lives only in DrawLine**  
`platform/wx_outputpane.cpp:1392`

*Trapped logic:* DrawLine turns a selection (two SelPoints, absolute character offsets) into painted rectangles across the visual rows of one logical line: selColStart/selColEnd derived per line with INT_MAX as the "selection continues past end of line" sentinel (1394-1408); a per-chunk overlap test chunkAbs1 > selColStart && chunkAbs0 < selColEnd (1436-1440); a three-way split of each chunk into before/inside/after with lo = max(0, selColStart - chunkAbs0), hi = min(chunk, selColEnd - chunkAbs0) (1442-1459); the wrap advance currentCol/globalChar that makes those offsets mean the same thing as the ones XToChar produces; and the trailing fill that paints the rest of the last row in the system HIGHLIGHT colour when the selection runs on to the next line (1483-1497). This is the forward half of a mapping whose inverse (XToChar, wx_outputpane.cpp:1967 — vrOffset * m_wrapCols + colInRow) is a separate implementation; the two must agree or the highlight marks different characters than Copy copies.

*Why unreachable:* DrawLine is private and has exactly one caller, OnPaint:1240. No selftest reaches OnPaint (they all exit inside wxApp::OnInit, so AppKit never issues drawRect:). grep for DrawLine across the repo returns only the declaration (wx_outputpane.h:528), that one call site, and unrelated wxDC::DrawLine calls in wx_gdi_compat.cpp.

*Symptom if broken:* Drag-select across a wrapped line (or with world.TextRectangle / a non-zero text pixel offset active) and the blue highlight lands on the wrong characters — one row's worth of columns off, or the second/third sub-segment drawn at the wrong x — while Cmd-C copies the correct text, because SelectedText() (wx_outputpane.cpp:3015) clips the range with its own independent arithmetic. Silent: it can only be seen by eye in the running app.

*Hoistable:* Yes, and it removes the duplicate-of-XToChar problem at the same time: extract a pure `std::vector<RowSegment> LayoutLine(int lineIdx, int wrapCols, int selStartCol, int selEndCol) const` returning {visualRow, colInRow, nChars, runIndex, selected} and make DrawLine a loop that only sets brushes and calls DrawRunChunk. The result is directly assertable headlessly-ish (it needs only m_lineChars/m_wrapCols), and a round-trip test LayoutLine ↔ XToChar pins the two mappings together.

**2. The mid-paint plugin-callback re-entrancy guard can never be armed by a test**  
`platform/wx_outputpane.cpp:1194`

*Trapped logic:* OnPaint sets m_inPaint = true around m_fn_draw_output_window (1194-1197), which fires ON_PLUGIN_DRAW_OUTPUT_WINDOW and therefore runs arbitrary plugin script between the under-miniwindow composite and the text pass. The state it arms is read in AppendLine (372-377): a line appended while painting is moved into a shared_ptr and re-posted via CallAfter instead of mutating m_lines / m_lineChars / m_visualRowStart / m_totalVisualRows underneath the loop that OnPaint is about to run (1236-1242). That is a real state transition with a defer-and-replay queue, not drawing.

*Why unreachable:* m_inPaint (wx_outputpane.h:773) is a private bool with no accessor — grep -n 'm_inPaint' returns exactly four hits, the declaration, the AppendLine reader, and the two writes inside OnPaint. Nothing outside the paint handler can set it, so the deferral branch in AppendLine has never executed in any build under test.

*Symptom if broken:* A plugin that prints from OnPluginDrawOutputWindow (world.Note / world.ColourTell, and Quow's status plugins do print on error paths) appends a line while OnPaint is iterating: m_visualRowStart grows and DropFrontLines may run mid-loop, so the pane reads a stale RowStartOf and either draws garbage rows or indexes past the end — a crash in the paint handler, on the user's machine only. The softer failure mode is the opposite: the CallAfter replay loses the line and the plugin's message never appears.

*Hoistable:* Yes: give the pane a public scoped `PluginDrawScope` (or BeginPluginDraw()/EndPluginDraw()) that OnPaint uses and a selftest can open directly, then AppendLine inside it, wxYield, and assert the line landed exactly once, after the scope closed, with LineCount and the wrap cache consistent. Same shape as the AdoptMeasuredMetrics/ApplyMetricsChange split already done here.

# The ranked plan

## Item 0 — DEFERRED (Wade, 2026-08-05)

**Decision: pinned for now. Revisit when it becomes a significant limiting
factor in test coverage.**

Work the hoistable items first — they are most of the list, they need no event
loop, and each one leaves the code better factored whether or not the loop mode
ever arrives. Build the loop-running mode only when what remains is genuinely
unreachable without it (realistically: the modal-dialog sequencing, items 14
and 16-19), and give it a watchdog timer from the start.

The downsides that informed the deferral: a selftest that fails to leave the
loop HANGS to the ctest timeout instead of failing, and per CLAUDE.md the
victim is usually a different, untouched test; real windows appear on screen
during every `ctest` run; paint-driven assertions become timing-dependent where
today they are synchronous. Against that, it probably retires the
`-ApplePersistenceIgnoreState` hazard, since an app that reaches `OnRun` is not
"crashing while launching".

The original analysis follows, unchanged, because it is what the revisit should
be argued against.

## Item 0 (original) — the one infrastructure decision that changes the cost of half this list

Fifteen of the twenty-four findings are unreachable for the *same* mechanical reason: every in-app selftest runs inside `wxApp::OnInit` and `std::exit`s before `OnRun`, so there is no event loop. That single fact is what makes `OnPaint` (findings 1, 2, 3), every `ShowModal` bridge hook (14, 16, 17, 18, 19), the update-UI idle pass (12, 19), and the deferred `CallAfter` in the TLS path (21) untestable — not their design.

Before working any individual item, decide whether to add **one loop-running selftest mode**: `OnInit` returns `true`, a `CallAfter` runs the harness body, and the body ends with `ExitMainLoop()` plus the exit code. Registration in `platform/wx_app.cpp` is unchanged; only the dispatch arm moves. That unlocks real `drawRect:` delivery, lets a modal complete (post `wxEVT_BUTTON` then `EndModal` from a `CallAfter`, as the finding-17 verifier established), and makes `wxUpdateUIEvent` arrive through wx's own idle pass rather than by hand.

Two side benefits worth weighing: it likely *removes* the `-ApplePersistenceIgnoreState` hazard recorded in CLAUDE.md, because an app that reaches `OnRun` and then exits is not "crashing while launching"; and it changes several items below from "hoist the logic out" to "just drive the real code". The risk is the obvious one — a selftest that fails to exit the loop hangs at the ctest timeout instead of failing. Cap it with a watchdog timer.

If you decline this, the cost estimates in Tier 3 roughly double, and findings 2, 16 and 17 become hoist-or-nothing.

## Tier 1 — do these first

### 1. TLS consent/fallback: the security downgrade decision (finding 21)
