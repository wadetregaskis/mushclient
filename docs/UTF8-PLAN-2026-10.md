# UTF-8: where it stands, and why it is built this way (2026-10-31)

The aim: UTF-8 everywhere, with no plugin broken silently.

## The model

A world's text is **bytes in that world's own encoding**. Scripts see those bytes,
exactly, whichever it is. That has not changed, and it is the compatibility story:

| | World marked UTF-8 | World not marked UTF-8 |
|---|---|---|
| Bytes a script sees | UTF-8 | what they always were |
| Server's non-UTF-8 byte | read as Windows-1252 | kept as it is |
| A control (command box, dialog) | real characters | real characters, in the world's code page |
| Who gets one | every **new** world | every **existing** world without `utf_8` |

The application around the worlds (file names, its own settings, menus and message
boxes) is UTF-8 in the 64-bit builds, through the manifest's `activeCodePage`.

Win32 keeps the machine's code page. It is the build for 5.x's ActiveScript, whose
VBScript and JScript read BSTRs as text.

## Why existing worlds are not converted

The first plan was to make all internal text UTF-8: decode each world's bytes at the
socket and each plugin file when loaded, and treat invalid UTF-8 from a script as Latin-1
with a warning. A scan of real plugins killed it.

Scanned: 23 public repositories (about 440 plugins), read over the network, plus about
140 on this machine (the bundled set, Quow's, a 5.06 install; some counted twice). No
plugin was run. All numbers are from a byte scan, not from reading each plugin.

| Finding | Repositories |
|---|---|
| Declares `iso-8859-1` but is pure ASCII | nearly all |
| Non-ASCII, valid UTF-8 (mostly a stray symbol) | 6, one or two files each |
| GBK in Lua source, **including string literals** | `leoleegz/XYJ-MushClient-Plugin` (37 files) |
| `\xA7` as a separator in Lua patterns, `\xD8` between plugins | `MateriaMagicaLLC/mushclient-plugins` (8 files) |
| Python or Ruby threads | none, anywhere |

The GBK case decides it. A literal in a `.lua` file is compared with server text in
Lua, and never crosses a world method:

```lua
if line == "<GBK bytes>" then ...
```

Decode that server's text to UTF-8 at the socket and the comparison quietly stops
matching. No boundary sees it, so no warning can fire. That is the silent breakage
this was meant to rule out, and it would land on a whole community of Chinese MUDs.
Materia Magica's `[^\xA7]*\xA7` would also change meaning: Lua's character classes are
bytewise, so the two bytes of a UTF-8 `§` are two separate class members.

So a world that is not UTF-8 stays in its bytes, and what changes is only how those
bytes reach Windows. Converting an existing world is the user's choice (tick UTF-8 on
its Output page), for a world whose plugins they know.

## The edges, and what was measured

**Process code page.** Trialled on a branch, with `activeCodePage=UTF-8`:

- `GetACP` is 65001, and `CP_THREAD_ACP` resolves to it even after `SetThreadLocale`.
- MFC's multi-byte mode goes byte-wise (`_getmbcp` is 0, `_ismbblead` false), which is
  safe for UTF-8: ASCII bytes never occur inside a multi-byte character.
- `MakeUpper` and `CompareNoCase` go ASCII-only, so case-insensitive matching of
  non-ASCII letters in those paths stops. (PCRE has its own tables.)
- File names work: `fopen` with a UTF-8 name made a file with that real name.
- An ANSI edit control round-trips UTF-8, and counts `EM_GETSEL` in UTF-16 units.
- **A Latin-1 or GBK byte in any ANSI control comes back as `EF BF BD`.** Silently,
  and it would be saved. Everything below exists because of this.
- `GetTextExtentPoint32A` follows the font's character set, not the process's code
  page, so a non-UTF-8 world's output window, drawn with `ExtTextOutA`, is unaffected.
- 1778 of 1781 tests passed under it unchanged. The three were all this same issue.

**Scripts.** World methods return strings in BSTRs (`SetUpVariantString`, and 99 Lua
functions through `pushVariant`). Under the manifest, and on a double-byte machine, a
world's non-UTF-8 bytes did not survive that. In the 64-bit builds a BSTR from a world
method is now just a carrier, each byte as one Windows-1252 character (`script_text.h`).
1252 is the only ANSI code page that maps all 256 bytes and back, measured:

| Code page | UTF-8 text | Latin-1 text |
|---|---|---|
| 1252 | intact | intact |
| 932, 936, 949, 950 | damaged | damaged |
| 65001 | intact | damaged |

**Controls.** MFC would convert through the process's code page, which knows nothing
about the world. So the command box and `DDX_Text` in a world's dialogs use the wide
APIs and convert with the world's own code page (`text_edges.h`): `CP_UTF8`, or the
code page of its output font's character set, or the machine's real ANSI code page.
This does not depend on the manifest at all, so it also fixed the Win32 build's UTF-8
worlds. Before it, a UTF-8 world's trigger showed `cafÃ© æ—¥æœ¬` in its dialog, and
typing `café` sent a bare Latin-1 byte to a UTF-8 server.

**Typing.** Messages fetched narrow turn any character needing three UTF-8 bytes into
`?`. `CMUSHclientApp::PumpMessage` fetches them wide (`HandleWideCharMessage`).

## Known gaps

- **List views in a non-UTF-8 world.** The trigger, alias, timer and variable lists use
  `SetItemText`, so a non-ASCII entry shows `�` under the manifest. Only the display:
  the value and the edit dialog are right.
- **Spell check selection** still counts UTF-16 units against bytes, when the command
  box holds non-ASCII and only part of it is selected.
- **The keypad page** reads and writes its fields directly, not through `DDX_Text`, so
  a non-ASCII keypad command in a non-UTF-8 world is not safe to edit under the
  manifest.
- **Title bar and status bar** in a non-UTF-8 world show `�` for non-ASCII under the
  manifest. Display only.
- **Tcl** re-encodes bytes that are not valid UTF-8, in a non-UTF-8 world.
- **Input method editors** were not available to test. `WM_IME_CHAR` is handled and
  edit controls handle composition themselves, but no IME has been run through this.
- **The Win32 build** has no manifest change, so the command box, being an edit control
  that MFC has subclassed, holds only what the machine's code page can: a UTF-8 world
  there reads and sends accented Western letters properly, but not kanji. Dialogs that
  MFC has not subclassed do show them.
- **Windows before 10 1903** ignores `activeCodePage`. The world edges still work, but
  the application's own text stays in the machine's code page.
- **Settings saved in an older code page.** A non-ASCII data-folder path saved by an
  earlier build is not valid UTF-8 under the manifest.
- **The port** has only the shared parts. None of it has been compiled.
